# Risks and Open Questions — Olive Grove Assistant

Current scope and terms live in [`CONTEXT.md`](../CONTEXT.md); the [domain model](domain-model.md)
describes concepts, and feature specs hold detailed decisions and evidence. This register contains
unresolved risks and evidence gaps. Remove resolved questions from the open tables and keep their
record in the owning spec or acceptance record. [`PROGRESS.md`](../PROGRESS.md) summarizes the
current implementation limits and manual checks.

## High risks

| Risk | Why it matters | Current mitigation / next action |
|---|---|---|
| Unsupported or outdated legal answer | A user could act on incorrect deadlines, amounts, or requirements | Use approved official sources, visible citations and verification dates, abstention, and targeted evaluation for critical claims. Assign a human owner for corpus review before real-user release. |
| Backend legal coverage is bounded | A working route could be mistaken for broad legal coverage | Publish the approved corpus boundary, cite only reviewed source passages, and abstain outside the three-topic Andalusia PAC 2026 slice. |
| Land context is wrong or incomplete | An answer could appear personalized while applying to the wrong land | Treat unknown as unknown; use all lands by default; ask for a land choice when answers differ; show which land context was used. Never infer eligibility from stored details. |
| Low digital confidence blocks adoption | The intended audience may abandon setup or misread a result | Keep the first journey short, explain terms in plain Spanish, allow general questions without setup, and observe low-confidence users completing key tasks. |
| Local device loss removes land records | Land data is deliberately local and no service-side copy exists | **Decision:** remain local-only; require same-device automatic copies and a portable, user-managed backup file before pilot. Recoverable removal, bounded same-device automatic copies, and the portable plaintext backup file (`portable_land_backup`) are implemented and accepted. Without an exported file, device loss, uninstall, or losing the app data area still permanently removes records because every app-managed copy lives on the same device; an exported file is unencrypted and its safekeeping is the person's responsibility. Never describe the on-device copies as protection from device loss. See [decision record](specs/land_backup_decision.md) and [`local_land_auto_backup`](specs/local_land_auto_backup.md). |
| Sensitive farm information reaches logs or infrastructure providers | Questions and minimal land attributes transit the hosted API and tunnel; user text may identify a person or operation | Keep land names/notes out of requests and logs; Gemini is planned but gated off until current model terms and data flows receive qualified review; no provider call is permitted before that gate. Question/answer retention is implemented default-off, per-question opt-in, redacted, without land context or stable IDs, and deleted within 30 days (`pilot_privacy_readiness`); pattern-based redaction can still miss personal details, and the pilot preflight blocks until a dated qualified review is recorded. Qualified privacy/legal review and current host/tunnel terms are required before pilot. The pilot runtime now authenticates each client, applies a per-worker per-client limit, bounds the request body, and writes only method/path/status/duration/gate; that code is tested locally but no hosted instance, tunnel, or provider log configuration exists, so it is not yet evidence that real traffic is protected. |
| Hosted deployment and recovery are unexercised | The pilot procedure, service unit, tunnel template, backup/restore, and rollback have no host or provider rehearsal; a failure mode could surface for the first time with users | The launcher, guards, preflight, readiness, backup, restore, and smoke commands are exercised locally against the canonical corpus, and the repair round rehearsed the clients-file permission path, the stop/restore/start sequence, and a backup-with-credentials refusal (see [`hosted_pilot_operations`](specs/hosted_pilot_operations.appendix.md)); the unit, tunnel, TLS, DNS, provider account, capacity, and multi-worker behaviour remain unverified. The restore guarantee is per-file atomic replacement with validation before writing and re-run recovery after a crash, not a single pair swap. Run the first-deploy, bad-config, restore, and rollback drills on the attested server before inviting anyone. |
| The pilot client cannot present the service token yet | Server-side authentication is now required by the pilot profile, but the Android/Desktop client sends no credential, so enabling the gate with the current app makes `/ask` fail | Add client credential support and a private delivery path in the client before routing pilot users; until then the app would show its accepted failure notice, not a wrong answer. |
| Per-process rate limiting, unauthenticated guesses, and single-host availability | Limits reset on restart and multiply by worker count; unauthenticated failures are not rate-limited; one host with no failover means any host loss is an outage | Treat the configured limits as protective defaults, not measured capacity; record the worker count in the deploy record; require long random tokens; add edge/IP failure limiting, external monitoring, and a support decision separately. Never present the pilot as highly available or as having an SLA. |
| No agreed pilot support channel | A pilot user has no concrete way to report an outage or a bad answer; the runbook names only the owner role | Before the first invitation, record the concrete support address and who monitors it in the pilot invitation and operator log. Do not invent an address or an SLA; until it is recorded, the support path is unset. |

| Unreviewed or malicious content enters the knowledge corpus | The assistant may follow misleading text or cite unreliable material | Restrict ingestion to approved sources, preserve provenance, treat document text as data, and require human review for additions or changes to critical material. |
| No hosting-enforced review gate for local update packages | A local draft package is not a pull request, so the hosting provider cannot enforce branch protection; anyone with filesystem access can still edit canonical files directly | The controlled merge verifies approval from a requested reviewer, matching package/checks/case digests, and passing checks before writing, and refuses known automation identities. Those identities and decisions are not authenticated, so this remains a procedural boundary. Add Git/hosting integration and provider-enforced protection before relying on it for unattended operations. |
| Active PAC campaign is misconfigured or stale campaign artifacts remain | A valid answer could use evidence for the wrong campaign | Require explicit four-digit `MANIJERO_ACTIVE_CAMPAIGN`; rotate expired source records and passages together after review; configuration is not inferred from date or question. |
| Free service limits or terms change | Costs, privacy, or availability can change after launch | Keep provider adapters replaceable, measure usage, define graceful rate-limit behavior, and do not promise zero ongoing cost until verified. |

| Official source updates are missed or misclassified | A scheduled scan can fail, an official page can change format, or an amendment can be ambiguous | Allowlisted scans now have a best-effort owned-host scheduler (`knowledge_update_scheduler`): an inert systemd timer template, target-level retries, a run ledger, and `status` alerts for missed, interrupted, failed, and stale runs; it is not installed or rehearsed on a host, has no external dead-man's switch, and its BOE/BOJA calendar assumptions are not live-verified. Quarantine candidates, run the read-only change-impact analysis, and require human approval before canonical knowledge changes. The analysis only reports explicit wording, so a missed or ambiguous change remains possible and detection quality is unmeasured.
| Knowledge release and rollback are rehearsed only locally | The `knowledge_release.py` prepare/publish/rollback path and the opt-in `MANIJERO_KNOWLEDGE_RELEASE_ROOT` read path have no host, systemd, tunnel, or off-host-backup rehearsal; a host-specific permission, disk, or symlink issue could surface for the first time with users | Rehearsed on the development Mac with temporary roots and a loopback uvicorn: publish, publish without restart, failed-gate refusal, tamper -> generic `503`, and rollback (see [the release appendix](specs/knowledge_reindex_release.appendix.md)). Still open: where the release root lives on a host, how it is backed up off-host, garbage collection of old releases, and the Chroma-packaging path, which was not run because the hybrid runtime is not installed here. The reviewed-baseline approval and code revision are recorded, not verified. Rehearse publish/rollback on the attested host before relying on it. |
| Local embedding/index capacity is unknown for the deployment host | bge-m3 and Chroma may exceed owned-server storage or memory limits | Measured only on the local development Mac: a 2,293,315,747-byte artifact, a 928 MB optional runtime, 1,943 MB peak RSS while embedding, about 77 ms for a two-text probe, and a 124,691-byte index over four passages. That is not an owned-server measurement. The pinned artifact and the Chroma store stay optional and off the default `/ask` path; hybrid ranking is an explicit opt-in that falls back to BM25. On the same Mac the hybrid runtime environment is 1.2 GB, the Chroma store over four passages is 630,124 bytes, a hybrid `/ask` run peaked at 1,967.5 MB RSS, and hybrid search took 33.9 ms median / 52.9 ms p95 per question. Measure the actual host before enabling hybrid there, and keep the BM25 rollback (unset `MANIJERO_RETRIEVAL_MODE`). See [the embedding appendix](specs/local_bge_m3_embeddings.appendix.md) and [the hybrid appendix](specs/chroma_hybrid_retrieval.appendix.md).

## Medium risks

| Risk | Why it matters | Current mitigation / next action |
|---|---|---|
| Several lands differ in relevant attributes | Broad operation-level answers may hide important differences | Use a land-aware clarification with names and relevant attributes; evaluate mixed dryland/irrigated and production cases. |
| User does not know an attribute | Forced form choices encourage inaccurate data | Support “I don't know” and allow editing later; the required zone and optional variety/surface/trees leave unknown attributes unknown. |
| Longer land setup for low-confidence users | The new required zone and ten-option variety list may lengthen setup without target-user evidence | Treat the field set as a product decision, keep plain-Spanish help and `No lo sé`, and validate comprehension and setup time with intended users before claiming the form is user-validated. |
| Critical sources contradict each other or show amendment history | Search can surface an obsolete rule beside a current one | Model validity/version relationships and show the relevant source/date; abstain when status cannot be established. |
| Shared UI behaves differently on desktop and mobile | Small-screen assumptions can make desktop awkward and future iOS expensive | Keep behavior and reusable UI shared where practical; adapt layout to form factor; avoid platform-only dependencies in common code. |
| Evaluation favors conventional, dryland users | Results may not cover irrigated, organic, or mixed cases | Record scenario coverage and gaps; label unvalidated coverage plainly and avoid overstating quality. |
| PAC answer-evaluation sample is narrow | A report could be mistaken for broad answer quality or legal validation | Keep metrics report-only; publish the exact 14-case, three-topic and five-boundary matrix and the eight out-of-scope omissions in [`pac_coverage.md`](../knowledge/pac_coverage.md). The report makes no quality or legal claim and does not represent untested questions. |
| Known PAC answer-evaluation misses remain | Three citation/critical-fact cases still cite a different reviewed passage, and an out-of-scope reclamación question now receives the modification deadline | Keep every mismatch visible in the per-case report instead of removing the case. Retrieval relevance is lexical and has no intent classifier or judge; resolving these would require a separate, measured retrieval/abstention change. Review is author-only; no independent legal validation or broad quality claim is supported. |
| Summary totals read as a verified or cadastral measurement | A person, or someone reading over their shoulder, could treat `Superficie anotada` / `Olivos anotados` as an official or measured figure | The wording says `anotado`, every card carries an `x de y` denominator, nothing annotated reads `Sin datos` and never `0 ha`/`0 olivos`, and the summary is never used as eligibility information. **No user test yet**: the design assumes the wording is understood; validating it with intended users, including low digital confidence, stays outstanding. |
| Search cannot find a land the person expects | A blank or unexpected result may read as “my land is gone” instead of “this word is not in the record” | Search covers only name, zone, municipality, variety (or custom `Otra` text), water regime and production method; the hint names those fields and the results keep the stored order. Searching by surface or tree count is deliberately unsupported. **No user test yet**: expect questions about why a measure does not match. |
| Refreshed chat, lands, and help screens have incomplete device and user evidence | Host-rendered screenshots do not prove device behavior, screen-reader output, or that people with low digital confidence can complete the flows. | Complete the manual checks and owner review listed in [`PROGRESS.md`](../PROGRESS.md) and the relevant feature acceptance records before making usability claims. On compact chat the `Preguntar` action may require a short scroll; confirm that cost before release. |

## Open decisions

### Blocking next phase

| Decision | Why it matters | Owner / trigger |
|---|---|---|
| Are land records recoverable enough for a private pilot? | Recoverable removal and bounded same-device automatic copies are implemented; a lost device, a deleted app, or a cleared data directory still removes every copy, and the user-controlled backup file only helps if the person exported one. | **Decision recorded:** stay local-only; require recoverable removal, same-device automatic copies, and portable plaintext backup/restore. All three are now accepted; portable backup/restore has no real-device picker or physical cross-device transfer evidence yet (see the [acceptance record](validations/portable_land_backup.md)). See `recover_removed_lands`, `local_land_auto_backup`, and `portable_land_backup`. |
| Can the owned server support the pilot, and which managed tunnel/provider is acceptable? | Host availability is still unverified; current provider terms were reviewed on 2026-10-27 but no path is approved for real-user traffic. | **Decision recorded:** Cloudflare Tunnel is conditionally selected as transport if the owned-server path is approved; the owned-server path itself stays blocked until the owner attests hardware, connectivity, power/backup, maintenance window, capacity, and recovery. Fly.io is the only evaluated fallback and is not approved. The pilot runtime now enforces application authentication, per-client (per-worker) rate limiting, a request-body bound, preflight/readiness, metadata-only logs, and a verified backup/restore command, all tested locally; a domain/tunnel/TLS setup, owner attestation, client credential support, external monitoring, and the qualified privacy/legal review remain pre-pilot conditions. See [the decision](specs/hosting_provider_review.md) and the [operator runbook](../backend/README.md). |

| Are private release signing and artifact links ready? | Install friction and signing/provider terms affect the pilot. | **Decision:** direct private links for Android APK and macOS Desktop installer only. Public stores, Windows, Linux, and iOS are out of scope. Signing/notarization and artifact-link provider requirements remain to be verified. |
| Is the question/answer retention design approved for real users? | Redacted free text may still contain identifying details and requires current legal/privacy review. | **Decision:** opt-in per question, default off; redacted Q/A text only, no land context or stable IDs, delete within 30 days — now implemented and technically gated (see [`pilot-privacy.md`](pilot-privacy.md)). **Reviewer outcome: none yet.** The committed review record is `pending`, so the pilot preflight reports `privacy_review_*` blockers and the Gemini gate stays closed. Still to be settled by the qualified review and the owner: the notice wording, the redaction limits, the participant-facing privacy/incident contact, whether per-person early deletion is required (records carry no identifier), the host journal retention, and current host/tunnel/Gemini terms. |

### Conditional decisions

| Decision | Trigger |
|---|---|
| Feedback and non-content operational trace retention | Before enabling either with real users; Q/A product-improvement retention is specified in `pilot_privacy_readiness`. |
| Which Gemini model/tier and whether its gate can pass | Gemini integration is planned for the private pilot, but outbound calls remain disabled until current official terms, data handling, limits/cost, and a qualified privacy/legal review are recorded. The gated drafting code now exists (`gemini_generation_provider`: minimal redacted payload, strict draft parsing, verify-then-extractive fallback), but it ships no transport and the limits file is committed all `null`; outstanding: a reviewed real transport (endpoint, region, credential storage, provider logging settings), the model id, the limits and spend cap, and both reviews. The 2026-10-27 review confirmed that EEA API clients require Paid Services, abuse monitoring retains prompts/context/output for 55 days and flagged content may be human-reviewed by authorized Google employees, project logs default to 55 days, and Spain is listed on Google's available-regions page; exact model/revision and tier, quotas/limits, serving-region routing, and the qualified review remain unresolved. See [the decision](specs/hosting_provider_review.md). **Owner decision (2026-10-31): postponed.** No spending for now; `local_generation_provider` is tried first on the owner's Mac, and paid Gemini is reconsidered for production only if local generation is insufficient. The local measurements are in [the `local_generation_provider` evidence](specs/local_generation_provider.appendix.md) ("Feature evidence"). Choices already made (free tier for synthetic development only, AI Studio for development, Vertex AI EU for the pilot, cheapest model) are in [the provider review](specs/hosting_provider_review.md). |
| Whether this Mac is enough to serve local drafting, or a faster server is needed | `local_generation_provider` pinned `mistral-small3.2:24b-instruct-2506-q4_K_M` (Apache-2.0) behind loopback Ollama and measured it on the owner's Apple M5 Max (64 GB) on the 14 reviewed author-only cases; the latency, cold-start, memory, and verified-draft numbers are in [the evidence](specs/local_generation_provider.appendix.md). The feature records numbers only and makes no recommendation. The owner decides from them whether this Mac is enough, whether an owned or external GPU server is needed, and whether local drafting may serve the pilot at all (which also needs the pilot review to cover local model drafting). |
| Whether local bge-m3 + Chroma/RRF improves retrieval enough to keep | `chroma_hybrid_retrieval` implemented an opt-in hybrid mode (RRF, `rrf_k` 60) and measured it on the 14 reviewed author-only cases on one Mac: answer metrics were identical to BM25 (13/14 states, 8/11 source and passage, 9/11 critical literals, 2/3 abstentions); top-5 retrieval recall of the expected passage went from 10/11 to 11/11 and MRR from 0.818 to 0.841, with two answers citing different passages. This is no evidence that hybrid improves answers. BM25 stays the default. Before changing the default, a larger reviewed case set, more than four passages, and owned-server capacity are needed. |
| How should supported discovery registries be scheduled reliably, and can FEGA/MAPA expose approved machine-readable registries? | Manual BOE and BOJA adapters are implemented; FEGA/MAPA remain explicit unchecked coverage gaps pending official evidence. `knowledge_update_scheduler` chose an owned-host systemd timer (daily monitor and BOE catch-up, weekly BOJA full-year discovery) and rejected GitHub Actions `schedule:`; missed/failed/stale runs surface through `run_source_updates.py status` and a failed unit only. Host installation, alert delivery beyond `systemctl --failed`/journald, and live calendar checks remain open. Discovery may propose candidates, but canonical additions require human approval. |
| Should knowledge update review move from a local draft package to real hosting-platform pull requests with provider-enforced merge protection? | Before relying on the review workflow for scheduled or unattended updates. The local package and controlled merge verify recorded approval but cannot enforce branch protection or stop direct filesystem writes; choose a provider/API and record its protection settings. |

### Later

| Question | Revisit when |
|---|---|
| Accounts, cloud sync, shared access, and multi-device restore | Users need continuity or collaboration across devices |
| SIGPAC references, parcel boundaries, maps, or multiple plots within a land | A validated workflow needs precise geographic records |
| Voice, document/photo interpretation, and offline assistant use | Accessibility and privacy constraints are understood and evaluated |
| iOS release details and native integrations | Android/Desktop MVP is stable; reuse shared logic and UI |
| Cooperative-facing review tools or content | A cooperative agrees to participate and boundaries are clear |
| Expanding automatic legal interpretation beyond source-change detection | Only after qualified legal review and a separately scoped approval model |
