# Domain Model — Olive Grove Assistant

This is the current conceptual product model, not a database schema. Use [`CONTEXT.md`](../CONTEXT.md)
for concise term definitions and the owning feature specs for exact fields, validation, persistence,
and request behavior.

## Person and device data

The MVP does not require an account. A **local user** means the person using one installation of the app. Their records are stored locally and are not shared across devices.

## Land

A **land** is an olive-growing area the user owns or manages. One local user can have zero or more lands.

Current land fields:

| Field | Meaning | Rule |
|---|---|---|
| ID | Stable local identifier | Generated by the app; never derived from a name |
| Name | User-chosen label, such as “Los Olivos” | Required; help users distinguish similar lands |
| Zone (paraje) | The place, path, or area the land is in, such as “Camino de la Fuente” | Required for every saved land. Never infer it |
| Municipality | Where the land is located | Optional until needed for an answer; do not infer it |
| Variety | The olive variety, from the approved shortlist, or unknown | Unknown is a valid state; `Otra` needs its own short text |
| Area | Optional user-entered approximate surface in hectares | Optional; accept comma or dot, store at most two decimals by rounding a longer entry, never infer |
| Tree count | Optional number of olive trees | Optional; a whole number of at least one, never infer |
| Water regime | Dryland, irrigated, both, or unknown | Unknown is a valid state |
| Production method | Conventional, organic, both, or unknown | Unknown is a valid state |
| Notes | Optional free text | Avoid sensitive personal details; do not use as trusted legal evidence |
| Created/updated | Local timestamps | Used for ordinary editing and recovery behavior |

“Both” can be represented as a deliberate selection where the user knows their land has mixed conditions. “Unknown” means they have not provided the detail. Do not treat unknown as both or as a default category. An absent surface or tree count stays absent; never render it as zero or a guess.

The zone, variety, custom variety text, surface, and tree count stay on the device. They are shown in the land list, the removal confirmation, and the clarification chooser, but they never enter the question payload.

### Land search and summary

The saved-lands list can be filtered by a text query and shows a summary of annotated values. Both are **derived, never persisted or sent**: the query lives only in the in-memory list state, resets on every read, and the summary is recomputed from the lands on screen. No store field, `Land`/`LandDraft` field, request or log line carries either.

The summary counts only annotated values and states its denominator (`x de y terrenos`, or `x de y encontrados` while a query is active), so a partial total never reads as a total for every saved land. An absent value stays absent: the card says `Sin datos`, never `0 ha` or `0 olivos`, and no total is inferred from another attribute. The wording says `anotado`, which is what the person wrote, and is not a verified, official or cadastral measurement.

Search matches text only: name, zone, municipality, the variety label or custom `Otra` text, the water-regime label and the production-method label. It never matches the id, notes, timestamps, surface or tree count, and it neither ranks nor reorders the stored records. It folds Spanish accents, `ñ` and case, and treats punctuation and emoji as word separators.

### Land lifecycle

```text
No lands → Add land → Active land → Edit details
                           └──────→ Confirm removal → Removed land
                                                       ├→ Restore → Active land
                                                       └→ Confirm permanent deletion → Deleted
```

- Removing a land now moves it to the local `Terrenos eliminados` list instead of deleting it
  ([`recover_removed_lands`](specs/recover_removed_lands.md)). The record keeps every field and stays
  there until the person explicitly restores it or permanently deletes it. Permanent deletion requires
  a second confirmation that names the land and removes the record from the app-managed store and every
  app-managed automatic copy of it; older exported files remain outside app control and can reintroduce
  their contents.
- A restored land returns to the **end** of the active list with its stored fields unchanged; the other active and removed lands keep their order. The removed list stays in removal order, so the newest removal is last. Removed lands never appear in the active list, the land chooser, or chat context.
- The store is the versioned aggregate `land-store-v2`, holding both the active and removed sections in one snapshot. An existing valid `land-store-v1` snapshot is migrated once on first read: every decoded record becomes active, the aggregate is written before the read returns it, and a refused migration write leaves the v1 store untouched and reports a failed read. Malformed records are skipped whole.
- Next to the aggregate the app keeps up to three **same-device automatic copies**, one after each committed change, each a whole aggregate with its own integrity metadata ([`local_land_auto_backup`](specs/local_land_auto_backup.md)). An unreadable aggregate is rebuilt from the newest fully valid copy and the app says so plainly; with no valid copy the read fails instead of showing an empty store. A partially readable copy is never treated as a complete restore. The copies live in the same app data area, use no network and no operating-system backup or device-transfer destination (the Android host excludes the land preferences from both), and do not protect against losing the device or uninstalling the app. Permanent deletion writes a durable purge marker before rewriting the store, filters the marked records from every read and restore, and clears the marker only after the aggregate and all retained copies are clean.
- A **portable land backup** ([`portable_land_backup`](specs/portable_land_backup.md)) is one plaintext JSON file (`format: manijero-land-backup`, `version: 1`) holding both lists in stored order plus an FNV-1a 64 checksum of the canonical land list. It is separate from the private `land-store-v2` codec and holds land data only (no chat, request log, device identifier, or account). Import validates the whole file (size ≤ 4 MiB, format, version, strict keys, checksum, every record value, ids unique across both lists) before a preview; restore then **replaces** both lists — never merges — after explicit confirmation, keeping a same-device automatic copy of the previous aggregate first. A refused file changes nothing. Exported files are user-controlled: the app never deletes them and they can reintroduce lands deleted after they were saved.
- An empty list is valid. The assistant remains usable for general questions and should explain when land details could improve an answer.
- Permanently deleting a land removes its local record for good and prevents future queries from using it. Ordinary removal is recoverable and does not delete the record. Previously saved conversations are not in MVP scope unless explicitly added later.

## Question and land context

A **question** is the user's original text plus the context chosen for answering. Keep the original wording for display and retry; do not silently change its meaning or log raw question text by default.

Context selection rules:

1. Use **all active lands by default** for questions that can be answered across the user's operation.
2. If an answer materially differs by land, ask the user to choose one or more named lands before producing a personalized answer.
3. If a required land detail is unknown, ask a plain-language follow-up or answer only the general part and state the limitation.
4. Never pick one land arbitrarily, silently treat all lands as identical, or claim that local data proves eligibility.
5. A question unrelated to land details should not require land selection.

The request sent to the assistant should contain only the minimum land attributes needed for that question, preferably stable local IDs plus relevant attributes. Avoid sending names or free-text notes unless the user explicitly asks a question that requires them. Do not put raw personal details in telemetry.

## Assistant response and source

An **assistant response** has one explicit state:

- **Answered:** evidence supports the response for the supplied land context; include citations and a verification date.
- **Abstained:** evidence is missing, stale, contradictory, or insufficient; explain the limitation and a suitable next step.
- **Needs land clarification:** applicable evidence differs across the user's lands; ask the user to choose the relevant land(s) before giving land-specific guidance.

Do not present a personalized answer while land clarification is pending. Preserve the original question across the clarification step. Candidate land choices come from the local land list; the assistant must not invent or rename a land.

A **source** is an approved official document or publication with a stable link, issuing body, relevant location (article/page where available), publication/update information, and last verification date.

- Each legal or regulatory claim must be traceable to one or more sources.
- Unsupported, stale, contradictory, or inapplicable evidence leads to an explicit limitation or abstention.
- For critical amounts and deadlines, show the supporting excerpt and source prominently.
- Land-specific context can guide relevance; it cannot substitute for the source of a legal rule.

## Relationships

```text
Local user 1 ── 0..* Land
Question ── 0..* Land context (all by default; narrowed by clarification)
Question + approved sources ── Assistant response
Answered response ── cited Source(s); abstained/clarification response ── explicit reason or next step
```

## Privacy and data lifecycle

- Land data stays on the device; a specific question may send only the contract-approved minimal land attributes for answer processing. Up to three automatic copies of the land aggregate stay in the same app data area and do not protect against device loss. Portable backups are plaintext, unencrypted, user-controlled files that can be moved between Android and macOS Desktop; the person decides where they live and the app cannot delete them.
- Explain that behavior in plain Spanish before first use; provide a way to inspect, edit, and remove saved lands.
- Do not log land names, notes, precise identifiers, or raw questions by default. Define retention and deletion for operational logs before release.
- Product-improvement retention is planned as default-off, explicit opt-in per question, redacted question/answer text only, no land context or stable identifiers, and automatic deletion within 30 days. It is not ready for real users until a qualified privacy/legal review is recorded.
- If the user changes or removes a land, future questions use the updated list. Do not imply prior answers were recalculated.

## Deferred concepts

SIGPAC geometry and references, multiple owners, shared access, cloud sync, accounts, tasks, assets, yields, expenses, aid calculations, and conversation history are outside MVP unless explicitly re-scoped.
