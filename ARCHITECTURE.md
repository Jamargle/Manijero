# Architecture

This document is the short map of stable ownership, dependency direction, and cross-system boundaries. Use feature specs for behavior and verification, and `PROGRESS.md` for current implementation status and limitations. Keep volatile state out of this file.

## Runtime surfaces and dependency direction

```text
androidApp ─┐
            ├──> shared
desktopApp ─┘

shared ──HTTP/JSON──> backend
```

- **`shared`** owns reusable Kotlin domain and presentation behavior, including Compose UI in `shared/src/commonMain`. Android and Desktop are hosts of that shared code. Platform entry points and integrations stay in `androidApp` and `desktopApp` or the corresponding `shared` platform source sets; shared code does not depend on either host.
- **`androidApp`** and **`desktopApp`** depend on `shared`. They provide launch/runtime wiring and platform-specific integrations; neither host depends on the other.
- **`backend`** owns the Python service and knowledge-backed request handling; it does not import app code. It reads local knowledge artifacts and exposes `GET /health`, `GET /ready`, and `POST /ask`. Endpoint behavior and operational rules belong in `backend/README.md` and the relevant feature specs.
- **`backend/app/pilot_config.py`**, **`pilot_guard.py`**, **`pilot_logging.py`**, **`readiness.py`**, and **`pilot_ops.py`** own the hosted-pilot runtime boundary: explicit profile/campaign/credential configuration, bounded request bodies, per-client authentication and rate limiting, the single operational request line, readiness separate from liveness, and the operator preflight/backup/restore/smoke commands. `backend/scripts/serve_pilot.py` is the only production-shaped launcher and `backend/scripts/pilot_ops.py` the operator entry point; `backend/deploy/` holds the service, tunnel, environment, and pinned-runtime templates. The development launcher (`./scripts/init.sh --backend`) is a separate local workflow with reload and no authentication.
- **`backend/app/source_monitor.py`** polls explicitly configured official feeds and writes monitoring state separately from canonical knowledge. It is dispatched manually or by an external owner-managed scheduler; it cannot update the approved catalog or passages.
- **`backend/app/source_discovery.py`** adapts documented BOE and BOJA registries into separate pending-candidate state. It is not an ingestion or answerability path.
- **`backend/app/document_ingestion.py`** fetches allowlisted pending candidates into a separate local quarantine, preserving original bytes/hashes and extracted page/section text. It never writes canonical knowledge or makes a candidate answerable; a human review and approval step remains separate.
- **`backend/app/change_impact.py`** reads the ingestion state and quarantine plus approved catalog, passages, and evaluation cases, and writes one deterministic impact report outside `knowledge/`. It is read-only: it never changes approved knowledge, never retires a source, and marks every potentially affected candidate as review-required. `backend/scripts/analyze_legal_changes.py` is its operator entry point.
- **`backend/app/review_package.py`** prepares a local, deterministic draft review package from quarantined candidates and a reviewed proposal. `prepare` and `decide` are read-only over canonical knowledge; a corpus change requires the reviewed evaluation case set and validates the after-state for orphaned cases. `merge` is the only path that writes the approved catalog/passages, and only after approval from a requested reviewer, matching package/checks/case digests, and an unchanged canonical baseline; it never reindexes or releases and preserves the field order of untouched entries. Its local draft does not depend on a Git/hosting API. `backend/scripts/knowledge_review.py` is its operator entry point.
- **`backend/app/embeddings.py` and `backend/app/embedding_index.py`** own the optional, pinned local embedding model and its derived passage index. A model may load only from a local directory after its immutable revision and every pinned SHA-256 verify, with hub access forced off; embeddings are off the `POST /ask` path, so the accepted BM25 retrieval and all code-owned answer properties are unchanged when the optional runtime or artifact is absent. The derived `passage-embedding-index-v1` file is operator-owned, refused under `knowledge/`, and never an answer source. `backend/scripts/manage_embeddings.py` is the operator entry point.
- **`contracts/`** owns the versioned, language-neutral HTTP wire contract. `contracts/openapi.yaml` is authoritative for request and response shape; examples are checked against it. Client DTOs and backend handlers conform to this contract.
- **`knowledge/`** owns reviewed knowledge artifacts and their JSON Schema formats. Executable validators live in `backend/app/` and must remain aligned with the schemas. Test fixtures are not canonical knowledge.

## Answer service boundary

`AnswerService.kt` defines the narrow shared interface and request/response DTOs. `KtorAnswerService` sends contract-shaped requests and maps transport failures to payload-free app errors. Shared presentation depends on `AnswerService`, not a Ktor engine or platform URL configuration. Hosts create and configure HTTP engines at their composition roots. Requests contain only the question and minimal land context; local land names and notes remain on-device. Platform-specific engine, endpoint, manifest, and lifecycle configuration is documented by the `platform_ask_wiring` feature contract and implemented in the host entry points.

## Hosted pilot boundary

The hosted pilot is **prepared but not operating**: the 2026-10-27 [hosting decision](docs/specs/hosting_provider_review.md) conditionally selects an owned server with a managed tunnel as transport, and that path stays blocked until the owner attests the host and the required privacy review is complete. No host, tunnel, TLS edge, or provider account is provisioned. The repository supplies the reviewed shape for that path. The tunnel would terminate TLS and forward to a loopback origin; it is transport, not authentication. The application owns access control: a per-client bearer token stored as a digest, that client's per-minute allowance, a bounded request body, explicit campaign configuration, preflight and readiness before traffic, and a single request-metadata log line that excludes question text, land values, client identifiers, and tokens. In that prepared shape the knowledge artifacts are read-only while the service runs, a corpus change is a reviewed deploy rather than a runtime write, and a restore is performed with the service stopped. `GET /health` stays liveness-only and `GET /ready` reports whether the configured campaign and corpus can answer. Deployment, credential ownership, backup/restore, rollback, access rotation, and outage response are procedural runbook steps in `backend/README.md`; they are not runtime behavior and have not been executed on a host.

## Privacy, retention, and review boundary

The data-flow inventory is [`docs/pilot-privacy.md`](docs/pilot-privacy.md). `AskRequest` carries an optional `retain_for_improvement` boolean that the shared chat sets only from an explicit, unchecked-by-default, per-send checkbox (and drops when the wording contains a saved land's private label). `/ask` produces its answer first; only then does a separate step (`backend/app/retention.py`) keep a conservatively redacted (`backend/app/redaction.py`) question and final answer in an owner-only SQLite file, and only when `MANIJERO_RETENTION_DB` is configured. The record holds no land context, identifier, or precise time and is purged no later than 30 days after creation; any retention failure leaves the answer unchanged and is logged only as a fixed code. Pilot preflight evaluates the recorded qualified privacy/legal review (`backend/config/pilot_privacy_review.json`, `backend/app/privacy_review.py`) and blocks the pilot while it is pending, which it currently is. Generation stays extractive: a configured Gemini provider is reported but never called, its separate review gate is closed, and `minimal_provider_payload` defines the only data (question plus approved passages) a future gated provider may receive.

## Data and platform boundaries

- Backend processing uses local knowledge artifacts; land records are stored on-device and are not backend storage. Current corpus contents, service availability, and evaluation limitations are tracked in `PROGRESS.md`.
- The local land aggregate lives in one versioned `land-store-v2` value behind `LandStorage`. The Android `SharedPreferences` and Desktop `FileLandStorage` adapters also implement `LandSnapshotStorage`: up to three same-device rotating copies of the whole aggregate, each with integrity metadata, plus a durable purge marker. Copies are written only after a successful primary write, a damaged primary is rebuilt from the newest fully valid copy or the read fails, and a permanent deletion reaches every retained copy. This is same-device recovery only: it has no cloud, network, or operating-system backup destination, and it does not survive losing the device or app data. The Android host backs that promise in the manifest: `manijero_lands.xml` is excluded from both `android:fullBackupContent` and `android:dataExtractionRules` (cloud backup and device-to-device transfer), and `AndroidBackupExclusionGuardTest` guards it; the Desktop store writes only under the local app data directory and configures no backup destination.
- The **portable land backup** is a separate external contract from the private store: `LandBackupFormat` (commonMain) owns the versioned plaintext JSON schema, its strict whole-file validation, and the export mapping; `LandBackupController`/`LandBackupScreen` own preview and replace-all confirmation; `LandRepository.replaceAll` is the only restore write (pre-restore same-device copy first, then one aggregate write). File selection crosses the platform boundary through the `LandBackupFiles` interface only: `AndroidLandBackupFiles` (shared `androidMain`, Storage Access Framework launchers registered by `MainActivity`) and `DesktopLandBackupFiles` (shared `jvmMain`, `java.awt.FileDialog`, wired in `desktopApp`). Shared code never sees a path or URI, no storage permission is requested, and no adapter uses a network, account, or cloud destination.
- Android and Desktop are current hosts; shared business behavior and Compose UI belong in `shared/src/commonMain`, while platform integrations remain in host or platform source sets. Other platform support is not implied by the shared source layout.

## Contract map

| Boundary | Authority | Consumers / implementation |
|---|---|---|
| HTTP wire shape | `contracts/openapi.yaml` and validated examples | Shared client DTOs; backend handlers |
| Knowledge artifact shape | `knowledge/*.schema.json` | Matching validators in `backend/app/` |

When adding a knowledge schema, keep its validator and fixtures aligned. Update this document when ownership, dependency direction, runtime boundaries, or contract authority changes; put endpoint rules, configuration details, and feature behavior in their owning docs instead.
