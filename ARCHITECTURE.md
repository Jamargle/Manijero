# Architecture

This document is the short map of stable ownership, dependency direction, and cross-system boundaries. Use feature specs for behavior and verification, and `PROGRESS.md` for current implementation status and limitations. Keep volatile state out of this file.

## Runtime surfaces and dependency direction

```text
androidApp ─┐
            ├──> shared
desktopApp ─┘

shared ──HTTP/JSON──> backend
```

- **`shared`** owns reusable Kotlin domain and presentation behavior, including Compose UI in `shared/src/commonMain`. Android and Desktop are hosts of that shared code. Platform entry points and integrations stay in `androidApp` and `desktopApp` or the corresponding `shared` platform source sets; shared code does not depend on either host.
- **`androidApp`** and **`desktopApp`** depend on `shared`. They provide launch/runtime wiring and platform-specific integrations; neither host depends on the other.
- **`backend`** owns the Python service and knowledge-backed request handling; it does not import app code. It reads local knowledge artifacts and exposes `GET /health`, `GET /ready`, `GET /metrics` (privacy-safe Prometheus counts and timings, `backend/app/health_metrics.py`), `POST /ask`, and `POST /feedback` (one fixed rating, `backend/app/feedback_api.py`). Endpoint behavior and operational rules belong in `backend/README.md` and the relevant feature specs.
- **`backend/app/pilot_config.py`**, **`pilot_guard.py`**, **`pilot_logging.py`**, **`readiness.py`**, and **`pilot_ops.py`** own the hosted-pilot runtime boundary: explicit profile/campaign/credential configuration, bounded request bodies, per-client authentication and rate limiting, the single operational request line, readiness separate from liveness, and the operator preflight/backup/restore/smoke commands. `backend/scripts/serve_pilot.py` is the only production-shaped launcher and `backend/scripts/pilot_ops.py` the operator entry point; `backend/deploy/` holds the service, tunnel, environment, and pinned-runtime templates. The development launcher (`./scripts/init.sh --backend`) is a separate local workflow with reload and no authentication.
- **`backend/app/source_monitor.py`** polls explicitly configured official feeds and writes monitoring state separately from canonical knowledge. It is dispatched manually or by `source_update_scheduler.py`; it cannot update the approved catalog or passages.
- **`backend/app/page_monitor.py`** (CLI `backend/scripts/monitor_official_pages.py`) fetches explicitly configured FEGA, MAPA, and Junta PAC pages, keeps a bounded last-good normalized-text snapshot outside `knowledge/`, and writes a deterministic added/removed/changed report. It never fetches linked resources, executes scripts, changes canonical knowledge, or interprets legal meaning; a page change is a review signal only ([spec](docs/specs/official_page_change_monitor.md)).
- **`backend/app/source_discovery.py`** adapts documented BOE and BOJA registries into separate pending-candidate state. It is not an ingestion or answerability path.
- **`backend/app/source_update_scheduler.py`** (CLI `backend/scripts/run_source_updates.py`) wraps monitoring and discovery unchanged with due rules, BOE catch-up, target-level retries, an exclusive state-directory lock, an append-only `source-update-ledger-v1` JSONL ledger, and a `status` evaluation for missed, interrupted, failed, and stale runs. It runs on the owned host from inert systemd templates (`backend/deploy/systemd/manijero-source-updates.{service,timer}`), keeps all state outside the repository, needs no secret, and never claims freshness; no repository-hosted schedule exists.
- **`backend/app/document_ingestion.py`** fetches allowlisted pending candidates into a separate local quarantine, preserving original bytes/hashes and extracted page/section text. `backend/app/corpus_security.py` scans the extracted text in memory first: a nominal listing (beneficiary/admittee/excluded-person list or repeated personal-identifier shapes) or model-directed instruction is rejected with a fixed category, its record is rebuilt from provenance alone, and its quarantine directory is deleted, so no listing row, name, or instruction text is stored. It never writes canonical knowledge or makes a candidate answerable; a human review and approval step remains separate.
- **`backend/app/legal_document_parser.py`** (CLI `backend/scripts/parse_official_documents.py`) turns quarantined PDF candidates into derived page-mapped Markdown plus a provenance manifest under an operator-owned output root outside `knowledge/`, with optional lazy layout/table/OCR adapters that degrade one capability at a time. It never changes ingestion state, is never read by the answer path, and makes nothing answerable ([spec](docs/specs/legal_document_parser.md)).
- **`backend/app/legal_structure_chunker.py`** (CLI `backend/scripts/chunk_legal_documents.py`) turns that Markdown into deterministic article/chapter/annex chunks with the reviewed source title, heading path, page range, and catalog-approved validity, under an operator-owned output root outside `knowledge/`. It splits only on explicit Spanish heading lines, never infers validity, and is never read by the answer path or a merge ([spec](docs/specs/legal_structure_chunker.md)).
- **`backend/app/structured_chunk_index.py`** (CLI `backend/scripts/manage_structured_index.py`) rebuilds a derived BM25 and optional `bge-m3`/Chroma index from only reviewed chunk sets (catalog join plus approval evidence), outside `knowledge/`; fail-closed, validity copied from the catalog. `/ask` and `/ready` read it only with `MANIJERO_STRUCTURED_INDEX=on` in local development or QA, never in release gates or the merge ([spec](docs/specs/structured_chunk_index.md)).
- **`backend/app/change_impact.py`** reads the ingestion state and quarantine plus approved catalog, passages, and evaluation cases, and writes one deterministic impact report outside `knowledge/`. It is read-only: it never changes approved knowledge, never retires a source, and marks every potentially affected candidate as review-required. `backend/scripts/analyze_legal_changes.py` is its operator entry point.
- **`backend/app/source_validity.py`** (CLI `backend/scripts/check_source_validity.py`) turns the reviewed catalog, reviewed passages, and one accepted change-impact report into a derived `validity-review-v1` artifact outside `knowledge/`. It may read an already-expired catalog structurally, but it only proposes retirements, reviews, and additions for a human and never changes a catalog, passage, release, index, or `/ask` ([spec](docs/specs/validity_checker.md)).
- **`backend/app/relevance_classifier.py`** (CLI `backend/scripts/classify_candidate_relevance.py`) reads an `official-discovery-state-v1` file, calls only the pinned loopback model through `OllamaTransport`, and writes a suggest-only `relevance-review-v1` list outside `knowledge/` (label plus one procedure-map topic per candidate; flagged or unparseable cases become `unsure`). It never drops, admits, or changes a candidate, and never touches releases, indexes, or `/ask` ([spec](docs/specs/relevance_classifier.md)).
- **`backend/app/grounding_judge.py`** (CLI `backend/scripts/judge_grounding.py`) is the offline, evaluation-only semantic check: it drafts the reviewed and approved golden cases with the pinned generator in-process, asks a second pinned loopback model of a different family whether each draft sentence is supported by the passages it cites, and writes a `grounding-judge-report-v1` outside `knowledge/` whose scores are labelled unchecked against human review. It is never on the `/ask` path ([spec](docs/specs/semantic_grounding_judge.md)).
- **`backend/app/review_package.py`** prepares a local, deterministic draft review package from quarantined candidates and a reviewed proposal. `prepare` and `decide` are read-only over canonical knowledge; a corpus change requires the reviewed evaluation case set and validates the after-state for orphaned cases. `merge` is the only path that writes the approved catalog/passages, and only after approval from a requested reviewer, matching package/checks/case digests, and an unchanged canonical baseline; it never reindexes or releases and preserves the field order of untouched entries. Its local draft does not depend on a Git/hosting API. `backend/scripts/knowledge_review.py` is its operator entry point.
- **`backend/app/knowledge_release.py`** and **`backend/app/release_gates.py`** (CLI `backend/scripts/knowledge_release.py`) own the reindex-and-release step after an approved merge. A release is an immutable, content-addressed directory under an operator-chosen root outside `knowledge/` that holds byte copies of the canonical catalog, passages, and reviewed cases, a BM25 fingerprint, the gated evaluation report, and optionally a packaged embedding index and Chroma store. Its closed `knowledge-release-v1` manifest (`knowledge/knowledge-release-manifest.schema.json`) is written last. `release_gates.py` (structural, BM25 determinism, grounding, and per-case no-regression against the published release; it always forces BM25 and extractive generation; its structural pass also reports `corpus_security` when catalog metadata or passage text, including `location`, carries a model-directed instruction or personal-identifier text) is imported only by `prepare`/`verify`. Publication is one atomic swap of a relative `current` symlink under a lock, with an append-only log. When `MANIJERO_KNOWLEDGE_RELEASE_ROOT` is set, the stdlib-only `knowledge_release.py` is the service's opt-in corpus read path: each request resolves `current` once, verifies `gate.passed` and the catalog/passages hashes, and reads both files from that directory. When the variable is unset, the checkout's `knowledge/` is read unchanged.
- **`backend/app/embeddings.py` and `backend/app/embedding_index.py`** own the optional, pinned local embedding model and its derived passage index. A model may load only from a local directory after its immutable revision and every pinned SHA-256 verify, with hub access forced off; embeddings are off the default `POST /ask` path, so the accepted BM25 retrieval and all code-owned answer properties are unchanged when the optional runtime or artifact is absent. The derived `passage-embedding-index-v1` file is operator-owned, refused under `knowledge/`, and never an answer source. `backend/scripts/manage_embeddings.py` is the operator entry point.
- **`backend/app/vector_store.py`, `backend/app/hybrid_retrieval.py`, and `backend/app/retrieval_backend.py`** own the optional hybrid ranking. `vector_store.py` persists the pinned passage vectors in a derived Chroma collection (`chroma-passage-store-v1` manifest plus Chroma files, refused under `knowledge/`, no passage text) and reports freshness from the model pin, active campaign, and a digest of the admitted documents. `hybrid_retrieval.py` fuses the BM25 and vector rankings with Reciprocal Rank Fusion (`backend/config/hybrid_retrieval.json`) and composes into `Retriever` only through `Retriever.with_ranker`, so the retriever still owns eligibility, the lexical gate, and citation metadata. `retrieval_backend.py` is the light `/ask` dependency: BM25 unless `MANIJERO_RETRIEVAL_MODE=hybrid` is configured and the store is fresh, with every failure falling back to BM25. `chromadb`, `torch`, and the model load lazily and never at service import. `backend/scripts/manage_vector_store.py` builds, checks, and compares.
- **Mock answer service** (`shared/src/jvmTest/.../mock`, test-only): an embedded Ktor CIO server that serves only the committed `contracts/examples/` responses on `GET /health`, `GET /ready`, and `POST /ask`, bound to `127.0.0.1`, so the apps can be tried without Python. It lives in the `jvmTest` source set, is never shipped in an app or library artifact, and is started and stopped by `./scripts/init.sh --mock` / `--mock-stop`; selection rules are in the [`mock_answer_server`](docs/specs/mock_answer_server.md) contract.
- **`backend/app/local_rag_bootstrap.py` and `backend/app/pinned_download.py`** (entry point `backend/scripts/local_rag.py`, behind `./scripts/init.sh --local-rag-setup` and `--local-rag-status`) are an operator-only setup layer that the service never imports. They compose the existing environment, embedding, release, and Ollama CLIs into one guided setup and one read-only status check over a local home outside the repository. Their only network calls are the pin-derived upstream file URLs and loopback Ollama. `backend/app/local_rag_service.py` (behind `--local-rag-start`, `--local-rag-service-status`, and `--local-rag-stop`) is the operator-only launcher in the same layer: it runs the unchanged service from `backend/.venv-hybrid` on loopback only, without reload, with an allowlisted environment and a run record in the local home, and is never imported by the service.
- **`backend/app/environment_profiles.py`** (entry point `backend/scripts/environments.py`, behind `./scripts/init.sh --environments-status` and `--qa-settings-setup`) is the operator-only reader of per-environment settings, credentials, and knowledge release roots (`~/manijero/local`, `~/manijero/qa`; prod unconfigured) that later environment features must use ([spec](docs/specs/environment_profiles.md)).
- **`backend/app/notice_pipeline.py`** (entry point `backend/scripts/process_cooperative_notices.py`) is a developer-only consumer of the loopback Ollama transport: it turns anonymized cooperative notices into unreviewed review files outside `knowledge/` that the answer path never reads ([spec](docs/specs/local_notice_pipeline.md)).
- **`backend/container/`** holds the answer service image definition (`Dockerfile`, its allowlist `Dockerfile.dockerignore`, the digest-pinned `base-image.json`), the container entry point, and the fixed Ollama relay (container loopback `11434` to `host.docker.internal:11434` only). **`backend/app/local_container.py`** (behind `./scripts/init.sh --container-build`, `--container-start`, `--container-status`, and `--container-stop`) is the operator-only builder and launcher in the local-RAG layer: it packages the published local release and the pin-verified search model and runs the image in Docker Desktop on host loopback only. The service code is unchanged inside the image, and drafting stays in Ollama on the host ([spec](docs/specs/backend_container_image.md)).
- **`backend/app/qa_deployment.py`** (entry point `backend/scripts/qa_service.py`, behind `./scripts/init.sh --qa-deploy`, `--qa-update`, `--qa-rollback`, `--qa-status`, and `--qa-stop`) is the operator-only deployer of the QA answer service: it runs the built image as `manijero-qa` on host loopback `8100` and exposes it through Tailscale Funnel for made-up test data only. In the pilot profile the image entry point starts the service through `serve_pilot.py`, which accepts a pending privacy review only for `MANIJERO_ENVIRONMENT=qa` plus `MANIJERO_QA_TEST_DATA_ONLY=yes` (`privacy_review.pilot_gate`) ([spec](docs/specs/qa_server_deployment.md)).
- **`backend/app/knowledge_ops.py`** (entry point `backend/scripts/knowledge_ops.py`, behind `./scripts/init.sh --knowledge-updates-on`, `--knowledge-updates-run`, `--knowledge-updates-status`, and `--knowledge-updates-off`) runs the accepted discovery, classification, ingestion, impact, validity, and review-preparation steps as one budgeted (one hour), retried (2 retries per step) cycle from a launchd user agent at 10:20 on the owner's Mac; it stops at "ready for review", never publishes or writes `knowledge/`, and feeds the health dashboard's "Knowledge updates" box ([spec](docs/specs/knowledge_ops_orchestrator.md)).
- **`backend/app/qa_alerts.py`** (entry point `backend/scripts/qa_alerts.py`, behind `./scripts/init.sh --qa-alerts-setup`, `--qa-alerts-start`, `--qa-alerts-stop`, `--qa-alerts-status`, and `--qa-alerts-test`) is the operator-only, stdlib-only QA alerter: a launchd user agent runs its `check` every 5 minutes on the owner's Mac, looks at QA through Docker, loopback `/health`, `/ready`, `/metrics`, and the public Tailscale address, and sends fixed-text Telegram messages; it detects service problems only while the Mac is awake ([spec](docs/specs/qa_service_alerts.md)).
- **The local smoke harness** (`./scripts/init.sh --local-smoke`) is test tooling around the unchanged service and release wiring. The operator-only, stdlib-only `backend/app/local_smoke.py` (same layer, never imported by the service) checks the running service, then drives two test-only drivers: the Desktop driver in shared `jvmTest` (`smoke/`, run only by `:shared:runDesktopLocalSmoke`) and the Android driver in `androidApp/src/androidTest` (installed over the debug app and run with `am instrument`). Both use the pure smoke protocol in commonMain `connection/LocalSmoke.kt` and find screen states through the invisible `chat/ChatTestTags`. `./scripts/init.sh --qa-check` reuses that Desktop driver for the QA service: the operator-only `backend/app/qa_check.py` probes the QA address, then runs the test-only `:shared:runDesktopQaCheck` (`smoke/DesktopQaCheckRun`), which wires the QA environment and access-key classpath resources like the `Manijero QA` Desktop build, asks the fixed question, and presses `Útil` once ([spec](docs/specs/qa_real_device_check.md)).
- **The local load measurement** (`./scripts/init.sh --local-rag-load-test`, `backend/scripts/measure_local_load.py`) is operator-only and stdlib-only, never imported by the service. It measures the unchanged running service over loopback `POST /ask` with simulated clients and writes aggregate-only reports under the local home; its numbers are host-specific evidence, not capacity or a pass/fail gate ([spec](docs/specs/local_load_test.md)).
- **The demo rehearsal harness** (`./scripts/init.sh --demo-rehearsal`) is operator-only, stdlib-only tooling around the unchanged service ([spec](docs/specs/rag_demo_rehearsal.md)). `backend/scripts/demo_rehearsal.py` probes `/health` and `/ready`, makes two fixed `POST /ask` calls, and drives one temporary, synthetic `review_package.prepare` → unapproved `merge` (refused) → `record_decision` → `merge` cycle on a copy of `backend/tests/fixtures/change_impact`. It never imports into the service, writes nothing outside the temporary workspace it removes, and reads canonical `knowledge/` only to hash it; the live order and manual app steps are in `docs/demo-script.md`.
- **The usability results recorder** (`./scripts/init.sh --usability-record`) is operator-only: `backend/app/usability_results.py` and `backend/scripts/usability_record.py` write anonymous `P<n>` session results outside the checkout and are never imported by the service ([spec](docs/specs/usability_session.md)).
- **`contracts/`** owns the versioned, language-neutral HTTP wire contract. `contracts/openapi.yaml` is authoritative for request and response shape; examples are checked against it. Client DTOs and backend handlers conform to this contract.
- **`knowledge/`** owns reviewed knowledge artifacts and their JSON Schema formats. Executable validators live in `backend/app/` and must remain aligned with the schemas. Test fixtures are not canonical knowledge. `knowledge/procedure_map.json` is a reviewed taxonomy index of olive-grove procedures — not legal knowledge, an answer source, or a coverage gate.

## Answer service boundary

`AnswerService.kt` defines the narrow shared interface and request/response DTOs. `KtorAnswerService` sends contract-shaped requests and maps transport failures to payload-free app errors. Shared presentation depends on `AnswerService`, not a Ktor engine or platform URL configuration. Hosts create and configure HTTP engines at their composition roots. Requests contain only the question and minimal land context; local land names and notes remain on-device. Platform-specific engine, endpoint, manifest, and lifecycle configuration is documented by the `platform_ask_wiring` feature contract and implemented in the host entry points. Release wiring keeps that fixed base URL. Test builds inject `ConnectionTools` instead: `KtorAnswerService` then reads the base URL per request from `ActiveServiceAddress` (saved address, else the build default), and the `Conexión` probe (`KtorServiceStatusChecker`, `GET /health` then `/ready`) reuses the same client. Gating lives in the hosts: Android `src/debug` versus `src/release` variant source sets, and on Desktop the `manijero.testBuild` property set only on the Gradle `run` task ([spec](docs/specs/local_service_connection.md)).

Pilot bearer token ([spec](docs/specs/client_pilot_credentials.md)): the only source is the git-ignored `pilot-token.local` at the repository root (saved by `./scripts/init.sh --pilot-token-save`; `MANIJERO_PILOT_TOKEN_FILE` overrides the path for tests), read at build time and validated without echoing it, for test builds only (owner decision 5). Every Android variant declares `BuildConfig.PILOT_TOKEN`, but only `debug` reads the file (literal `null` without one); release is always the literal `null` and never reads it. Desktop generates `build/generated/pilotToken/manijero/pilot-token.txt` and appends that folder only to the Gradle `run` task's classpath when the task starts, so `jar` and every packaged or release output never contain it; jvmMain `desktopPilotToken()` reads the resource. Each host turns it into a commonMain `PilotToken` (redacted `toString`) and passes it to both `KtorAnswerService` branches. On each `ask` and each `sendFeedback` the transport adds `Authorization: Bearer …` only to that `POST /ask` or `POST /feedback`, only when the address resolved for it is `https`, or `http` to `localhost`, `127.0.0.1`, `[::1]`, or `10.0.2.2` (`mayCarryPilotToken`); probes never carry it. A refused token (`401`/`429`) is the existing payload-free service error. The shared transport's one-field rating ([spec](docs/specs/answer_feedback_ui.md)) sends only `{"rating":"useful"|"not_useful"}` to `POST /feedback`: no question, answer, land, source, index, device or client value travels, and the rating stays in memory with the transcript (unlinked, unpersisted).

Build environment ([spec](docs/specs/client_environment_builds.md)): the Gradle property `manijeroEnvironment` (`local`, the default, or `qa`) selects the target at build time; anything else fails the build. A QA build is a separate app: Android gets the `.qa` application id suffix and the label `Manijero QA`, and Desktop uses the title `Manijero QA` and its own data folder `~/.manijero-qa` (`manijero/environment.properties`, read by jvmMain `desktopEnvironment()`). QA takes its address from the git-ignored `qa-address.local` (or the placeholder `https://qa.manijero.invalid`), ignores the local address overrides, and sends the QA access key in test builds only; local builds never read either.

## Hosted pilot boundary

The hosted pilot is **prepared but not operating**: the 2026-10-27 [hosting decision](docs/specs/hosting_provider_review.md) conditionally selects an owned server with a managed tunnel as transport, and that path stays blocked until the owner attests the host and the required privacy review is complete. No host, tunnel, TLS edge, or provider account is provisioned. The repository supplies the reviewed shape for that path. The tunnel would terminate TLS and forward to a loopback origin; it is transport, not authentication. The application owns access control: a per-client bearer token stored as a digest, that client's per-minute allowance, a bounded request body, explicit campaign configuration, preflight and readiness before traffic, and a single request-metadata log line that excludes question text, land values, client identifiers, and tokens. In that prepared shape the knowledge artifacts are read-only while the service runs, a corpus change is a reviewed deploy rather than a runtime write, and a restore is performed with the service stopped. With a configured knowledge release root, a corpus change is instead `knowledge_release.py publish` of a gated release, and `rollback` is the corpus rollback; neither writes `knowledge/` or restarts the service, and both have been rehearsed only locally. `GET /health` stays liveness-only and `GET /ready` reports whether the configured campaign and corpus can answer. Deployment, credential ownership, backup/restore, rollback, access rotation, and outage response are procedural runbook steps in `backend/README.md`; they are not runtime behavior and have not been executed on a host.

## Privacy, retention, and review boundary

The data-flow inventory is [`docs/pilot-privacy.md`](docs/pilot-privacy.md). `POST /feedback` (`backend/app/feedback_api.py`) accepts only a fixed `useful`/`not_useful` rating: it stores nothing, adds no answer linkage, and contributes only a per-process `feedback_total{rating}` count. `AskRequest` carries an optional `retain_for_improvement` boolean that the shared chat sets only from an explicit, unchecked-by-default, per-send checkbox (and drops when the wording contains a saved land's private label). `/ask` produces its answer first; only then does a separate step (`backend/app/retention.py`) keep a conservatively redacted (`backend/app/redaction.py`) question and final answer in an owner-only SQLite file, and only when `MANIJERO_RETENTION_DB` is configured. The record holds no land context, identifier, or precise time and is purged no later than 30 days after creation; any retention failure leaves the answer unchanged and is logged only as a fixed code. Pilot preflight evaluates the recorded qualified privacy/legal review (`backend/config/pilot_privacy_review.json`, `backend/app/privacy_review.py`) and blocks the pilot while it is pending, which it currently is. Generation stays extractive. `backend/app/gemini_generation.py` holds a gated, replaceable Gemini drafting path behind the `GroundingGenerator` seam: `create_app` resolves the provider once at startup and selects `GatedGeminiGenerator` only when `MANIJERO_GENERATION_PROVIDER=gemini`, `MANIJERO_GEMINI_MODEL` matches the reviewed model, the pilot and Gemini review gates pass, the recorded limits file `backend/config/gemini_provider_limits.json` holds dated in-range timeout/token/rate/cost values (committed all `null`), and a `GeminiTransport` was injected. No transport exists in the repository, so the effective provider is `extractive` everywhere and nothing can leave the service. When active, the generator sends only `minimal_provider_payload` (the redacted question plus candidate-numbered excerpts of the citation window), strictly parses a `{status, answer, sources}` draft, runs `verify_draft`, and falls back to the extractive draft on any failure (verify-then-fallback); lead-in, notice, markers, and sources stay code-owned and the unchanged pipeline verifies the returned draft again. A second provider, `local` (`backend/app/local_generation.py`), drafts with a pinned open-weight model served by Ollama on the same host. It is off by default and selected at startup only when `MANIJERO_GENERATION_PROVIDER=local`, `MANIJERO_LOCAL_MODEL` equals the tag in the committed record `backend/config/local_generation_model.json` (exact tag, `/api/tags` digest, licence, size within a 50 GB budget, and limits), the record passes its gate, and, in the pilot profile, the pilot review has passed. It reuses `GatedGeminiGenerator` unchanged (same payload, parser, verifier, rate limiter, and extractive fallback); only its transport, `OllamaTransport`, is new. That transport talks only to the loopback constant `http://127.0.0.1:11434` (no configurable URL, no proxy, no redirect, no remote endpoint) and refuses a model whose installed digest differs from the record. Resolution makes no network call; the digest is checked on the first draft.

A local-only debug trace (`backend/app/answer_trace.py`) is off unless `MANIJERO_ANSWER_TRACE=on`: it writes one `answer-trace-v1` JSON file per `/ask` to the git-ignored `build/answer-traces/` folder (deleted after 7 days) with question, answer, and draft text only when `MANIJERO_DEPLOYMENT_PROFILE` is explicitly `development` (the local service start states it; an unset profile records no text) and ids, scores, timings, and verification codes everywhere else; it never changes an answer.

`/ask` first screens each question with deterministic rules (`backend/app/input_guardrails.py`): personal data, prompt injection, or an off-topic question returns a pinned abstention before retrieval, and a personal-data hit is never retained and leaves a metadata-only trace.

An in-memory answer cache (`backend/app/answer_cache.py`) sits in `ask_api._answer` after the year pre-check, corpus validation, retrieval attach, and land clarification: it is per process, empty at every start, on by default (`MANIJERO_ANSWER_CACHE=off` disables it), and holds only a SHA-256 key digest and the verified response. The key is the question normalized for case, accents, and whitespace, the land context, the knowledge identity (release id, admitted-passage fingerprint, campaign), and the model identity (provider model, retrieval mode, `k`, `max_claims`); every hit re-runs `verify_draft`, entries live at most 24 hours, and transient failures are never stored ([spec](docs/specs/answer_cache.md)).

A reviewed question glossary (`backend/app/question_glossary.py`, `backend/config/question_glossary.json`) appends owner-approved official terms to the retrieval query only, after retrieval attach; the grower's words stay first and every other step keeps the original question. Release gates never apply it ([spec](docs/specs/question_rewriting.md)).

In the same explicit `development` profile only, `/ask` adds an optional `inspection` object (`answer-inspection-v1`: retrieved passages, scores, drafting and verification codes; `backend/app/answer_inspection.py`). The client keeps it only for a test-tools host on a loopback address and shows it behind an `Inspeccionar` link.

## Data and platform boundaries

- Backend processing uses local knowledge artifacts; land records are stored on-device and are not backend storage. Current corpus contents, service availability, and evaluation limitations are tracked in `PROGRESS.md`.
- The local land aggregate lives in one versioned `land-store-v2` value behind `LandStorage`. The Android `SharedPreferences` and Desktop `FileLandStorage` adapters also implement `LandSnapshotStorage`: up to three same-device rotating copies of the whole aggregate, each with integrity metadata, plus a durable purge marker. Copies are written only after a successful primary write, a damaged primary is rebuilt from the newest fully valid copy or the read fails, and a permanent deletion reaches every retained copy. This is same-device recovery only: it has no cloud, network, or operating-system backup destination, and it does not survive losing the device or app data. The Android host backs that promise in the manifest: `manijero_lands.xml` is excluded from both `android:fullBackupContent` and `android:dataExtractionRules` (cloud backup and device-to-device transfer), and `AndroidBackupExclusionGuardTest` guards it; the Desktop store writes only under the local app data directory and configures no backup destination.
- The **portable land backup** is a separate external contract from the private store: `LandBackupFormat` (commonMain) owns the versioned plaintext JSON schema, its strict whole-file validation, and the export mapping; `LandBackupController`/`LandBackupScreen` own preview and replace-all confirmation; `LandRepository.replaceAll` is the only restore write (pre-restore same-device copy first, then one aggregate write). File selection crosses the platform boundary through the `LandBackupFiles` interface only: `AndroidLandBackupFiles` (shared `androidMain`, Storage Access Framework launchers registered by `MainActivity`) and `DesktopLandBackupFiles` (shared `jvmMain`, `java.awt.FileDialog`, wired in `desktopApp`). Shared code never sees a path or URI, no storage permission is requested, and no adapter uses a network, account, or cloud destination.
- The welcome-card dismissed flag is a separate device-local boolean (`WelcomeNoticeStore`: Android `manijero_welcome` preferences, Desktop `~/.manijero/welcome-v1.txt`). It holds no land or personal data, so the land backup exclusion does not cover it.
- Android and Desktop are current hosts; shared business behavior and Compose UI belong in `shared/src/commonMain`, while platform integrations remain in host or platform source sets. Other platform support is not implied by the shared source layout.
